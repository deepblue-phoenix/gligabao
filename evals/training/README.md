# Trained-model audits and evals (LLM as a judge)

Checks a trained model's answers with an LLM as the judge. The model is asked each case's question (`instruction`, plus `input` as context, as in training) and an external LLM, the one gligabao uses for knowledge ingestion (Anthropic, `ANTHROPIC_API_KEY`), judges how closely each answer agrees with the reference `output`. Two things use this engine. They share the Go types (`relational.TrainedModelRun` and `TrainedModelCase`, told apart by `Kind`), the statuses, the manager and the endpoints that follow a run (`internal/api/training/runs.go`), the judge and the admin UI's views; what differs is where the cases come from:

- An **eval** (`internal/api/training/evals.go`, kind `eval`, the `training` rows of the universal eval tables, HTTP `/evals`): the cases are those of an **eval**, a named set of cases of `bin/evals_training/*.json` that the model never saw, so the score says how well it generalizes. [docs/training/EVALS.md](../../docs/training/EVALS.md).
- A **training data audit** (`internal/api/training/audits.go`, kind `audit`, tables `gb_training_audit_runs` / `gb_training_audit_cases`, HTTP `/audits`): the cases are the model's **own fine-tuning dataset**, so the score says whether the training took (memorization / fit) and, through the examples it fails, which training data is bad. It does not measure generalization. [docs/training/AUDIT.md](../../docs/training/AUDIT.md).

Both are separate from the knowledge-extraction evals in [`../knowledge`](../knowledge/README.md). The outcome of one case is a `trainingeval.CaseResult` here, stored as a `relational.TrainedModelCase` (for an eval, a row of `gb_experiment_case_results` like a knowledge case's, with the case's name as its `case_name`).

## Running one

In the admin UI, training view, press **Eval** (or **Audit**) on a trained model (the table's last columns, or the sections of the model's dialog, which also let you pick the eval, ask only the first n cases and set the batch size). It runs in the background on the server; the dialog shows its progress, the score so far, and (expanding "Answers") every question with the expected answer, the model's, the score and the judge's reason, lowest score first. Each run has a **Watch live** button (and one opens when you start it): a dialog that follows its SSE feed, showing each question with the expected answer and the model's as soon as the model answers it, then its score and the judge's reason when its batch is judged, with a one-square-per-question strip, running totals, and an "only problems" filter. A run can be cancelled, and the batches done so far are kept. Over HTTP: [evals](../../docs/training/EVALS.md#api), [audits](../../docs/training/AUDIT.md#api).

For an audit the questions are those of the model's own training dataset, so the score says how closely the model reproduces its training answers (memorization / fit), not how well it generalizes.

## Evals and running them from the command line

The evals are in `bin/evals_training/*.json` (static definitions, kept in `bin/` next to the datasets, read from disk by `LoadEvals(dir, ...)` and `Evals(dir)`; the command takes `-evals dir`, the server `--training-eval-dir`): each file is an eval, named like the file without `.json`, and holds a list of cases `{name, instruction, input?, output}`, `output` being the expected answer. An eval is named after the training dataset its cases ask about; they ask about knowledge that is in the dataset but are phrased differently from its examples (several facts per question). `world-knowledge-base.json` has 10 cases on the `world-knowledge-base` dataset (`bin/datasets_training/world-knowledge-base/`). A model trained on a dataset has the eval of that name by default; any other eval can be asked for by name. The server lists them at `GET /v1/gb/training/eval-definitions`.

```
./run_evals.sh -t training -list-models          # the ids of the trained models in bin/gligabao.db
./run_evals.sh -t training [-model 3] [-v] [-e world-knowledge-base] [-no-store] [case-name ...]
```

Without `-model`, the model is the newest trained Gemma 4 4B one. It needs `ANTHROPIC_API_KEY` (the judge) and the sidecar (`SIDECAR_URL` or `-sidecar`; the model is loaded there): `run_evals.sh` starts it, as `run_server_local.sh` does, if a local one does not answer (needs `MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET`), and stops it at the end. The runner (`evals/training/cmd`) does what the Eval button does: it picks the eval (`-e`, else the one named like the model's dataset), asks the model each question, has the judge grade the answers with the same engine as below, prints a verdict per case and the totals, and **stores the run** in the database (`-db`; an eval run with its cases and the judge's recorded calls, which the admin UI shows), unless `-no-store`. A case is correct with a score of 4 or 5 (the engine's verdict, not a stored status: stored cases are `judged` or `error`); the exit status is 1 if any case is not correct. Other options: `-batch-size`, `-judge-model`, `-max-tokens`, `-temperature` (`go run ./evals/training/cmd -h`).

## How it works

1. The examples are read from the eval's cases (`LoadEvals`) or, for an audit, from the model's dataset (`ParseExamples`), the first `limit` of them if a limit is set.
2. They go in **batches** (`Config.BatchSize`, default 10, at most 25). For each batch the model answers the questions (`GenerateFunc`: one sidecar inference per question, strictly one at a time, in order), then **one** call to the judge LLM grades the whole batch, so n questions cost about n / batch size judge calls, not n.
3. The judge gets the batch as JSON (question, reference, answer per case) and a rubric, and replies with a JSON array of `{id, score, reason}`. Score is 0 to 5: 5 same as the dataset, 4 correct with minor differences, 3 partly correct, 2 mostly wrong, 1 wrong, 0 empty/nonsense/refusal. 4 and 5 count as **correct**, 2 and 3 as **partial**, 0 and 1 as **incorrect**. Wording, order and length do not matter, facts, numbers, names and actions do. The cases are given as data, with a rule to ignore any instructions in them. Texts over 4,000 bytes are cut before being sent.
4. Cases the judge skipped or answered with an invalid score are sent once more; still without a verdict they are marked error. A question the model failed to answer is marked error and not sent to the judge. The run stops with an error after 2 batches in a row where the model answered nothing, or 3 where the judge graded nothing (a dead sidecar, a bad API key), instead of burning GPU time.
5. After each batch the cases and the running totals (answered, judged, errored, correct/partial/incorrect, score sum, the judge's tokens and cost) are handed to a `Sink`, which the server stores, so progress is visible while the eval runs.

The package knows nothing about HTTP, the sidecar or the database: `Run(ctx, cfg, examples, generate, judge, sink)` takes the model as a function, the judge as an `LLM` (`Complete(ctx, ai.Request)`) and the results go to the sink. `internal/api/training/runs.go` wires them (for an eval and for an audit alike) to the sidecar, `memory_core.WithRecording` (so the judge's calls are in `gb_inferences`, as type `training_eval_judge` for an eval and `training_audit_judge` for an audit) and the database. Tests (`go test ./evals/training`) use a fake model and judge, no network.
