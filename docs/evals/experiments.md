# Eval experiments

An **experiment** is a named group of evals that are run together, plus the settings under test. Every time the eval runner (`go run ./internal/evals/knowledge/cmd`, `./run_evals.sh`) executes, it records one **run** of an experiment in the **eval** database (`build/gligabao-eval.db`), which keeps the evaluation data apart from the main database and is never reset. Each case run works in a dataset of its own (`<case>_run<eval run id>`), so runs do not interfere with each other. A run records which cases of which evals it executed, how each ended, and the IDs of the [ATIF trajectories](knowledge.md) of their calls. The code is [`internal/evals`](../../internal/evals/README.md): the structs are in `core`, the tables in `db/{sqlite,postgres}/schema.sql`, and the recording of the runs in `runner`.

## Data model

The knowledge-extraction evals and the [evals of trained models](training.md) share one set of tables, the `gb_*` tables. The **universal** tables hold what every eval has and carry a `type` column (`knowledge` or `training`); what only one type has is in that type's **metadata** tables, one row per row of the universal table. A composite foreign key `(parent id, type)` keeps the type the same down the chain: the database refuses a case def under an eval of the other type, a case run under an eval run of the other type, or metadata on a row of the other type. The vocabulary and the rules of the model are in [`core/doc.go`](../../internal/evals/core/doc.go).

**Terms.** There are two sides, and every concept exists on both:

| definitions (what to run; stored, reused) | runs (what happened; append-only history) |
|---|---|
| `ExperimentDef`: which evals, plus settings | `ExperimentRun`: one execution of an experiment def |
| `EvalDef`: a named collection of cases of one type | `EvalRun`: one execution of an eval def |
| `CaseDef`: one input and what is expected or checked | `CaseRun`: one execution of a case def |

An *eval case* (a *case*) is one input/output combination, plus metadata, to be evaluated. Cases are grouped into an *eval* (a set of cases). An *experiment* groups evals (an eval can be in many experiments). The definitions are stored in the database when a run starts (`runner.SyncEval` puts the evals of the JSON files in as defs, and rewrites a case def whose file changed); a run has a link to its def, and records the `params` it was invoked with, so it can be understood without looking at the def as it is now.

| table | struct (package `core`) | meaning |
|---|---|---|
| `gb_eval_defs` | `EvalDef` | `name` (unique), `type`, `description`, `tags`, `params` |
| `gb_case_defs` | `CaseDef` | a case of an eval: `name` and `position` (both unique within the eval), `type`; its type-specific part is in `gb_case_def_meta_<type>` |
| `gb_case_def_meta_knowledge` | `KnowledgeCaseDefMeta` | the texts to `remember`, the `query`, the checks (`expect_contains`, `expect_edges`, `expect_min_chunks`, `expect_web_searches`, `expect_series`, `expect_geo`) and the settings (`chunk_size`, `models`, `reasoning`) |
| `gb_case_def_meta_training` | `TrainingCaseDefMeta` | `instruction`, `input` and the expected `output` |
| `gb_experiment_defs` | `ExperimentDef` | `name` (unique), `description`, `params` (free-form JSON: the settings under test) |
| `gb_experiment_def_evals` | `ExperimentDef.EvalDefIDs` | the evals of an experiment, in the order they run |
| `gb_experiment_runs` | `ExperimentRun` | one execution of an experiment: `status`, `error`, `params` (how it was invoked), `counts_*` and `cost_usd` over the case runs of all its eval runs, `created_at`, `started_at`, `finished_at` |
| `gb_eval_runs` | `EvalRun` | one execution of an eval, in an experiment run or on its own (`experiment_run_id` is NULL): `type`, `status`, `error`, `params`, `counts_*`, `cost_usd`, times |
| `gb_eval_runs_meta_knowledge` | `KnowledgeEvalRunMeta` | the statistics of the run as a whole: `chunks`, `steps`, `remember_calls`, `query_calls` and their cost, `checks_passed`, `checks_failed` |
| `gb_eval_runs_meta_training` | `TrainingEvalRunMeta` | the trained model, the judge and the split of the scores, see [training.md](training.md#tables) |
| `gb_case_runs` | `CaseRun` | one case's result in an eval run: `type`, `status`, `error`, `verdict`, `score`, `cost_usd`, times |
| `gb_case_runs_meta_knowledge` | `KnowledgeCaseRunMeta` | `input` (as given), `answer`, `problems` (the checks that failed), `passed_checks`, `dataset_id` (the dataset the case ran in, which holds the knowledge graph it built; null if it was never created), `steps` (ATIF steps over its trajectories) |
| `gb_case_runs_meta_knowledge_trajectories` | `KnowledgeTrajectory` | the ATIF trajectories of a case, in call order (`seq`): `kind` (`remember` / `query`), `trajectory_id`, `agent_name`, `steps`, `cost_usd`, `path` of the JSON file, `artifact_ids` (the IDs, in the case's dataset, of the call's artifacts: the artifact a remember stored, or the artifacts a query's evidence edges were sourced from via the edge provenance links; the admin API resolves them to `artifacts` by reading the dataset) |
| `gb_case_run_commentaries` | `CaseCommentary` | the LLM commentaries on a failed case run, made from the admin UI (see [Admin UI](#admin-ui)): `model`, `text` (the commentary with its recommendation), tokens, `cost_usd` (not part of the case run's cost), `created_at`; several per case run if it was asked again, the newest counts; deleted with the case run |
| `gb_case_runs_meta_training` | `TrainingCaseRunMeta` | the question, the expected answer, the model's answer and the judge's score and reason, see [training.md](training.md#tables) |

Links between runs go from child to parent (`CaseRun.EvalRunID`, `EvalRun.ExperimentRunID`); a parent stores no list of its children. A def that has runs cannot be deleted (`ON DELETE RESTRICT`), so the history stays understandable; deleting a run deletes the runs under it and their metadata.

Both types have **evals**: a case belongs to an eval, and a case name is unique within its eval only (two evals may use the same name; a case named alone on the command line that more than one eval has is ambiguous, so name the eval too with `-eval`). Knowledge evals are the files of `build/evals_knowledge/`. Training evals are the files of `build/evals_training/` (named after the training dataset their cases ask about); an *eval run* (one run of the eval against one trained model) has one case run per case.

The graph and the artifacts of a case are not copied into the run tables: they are read from the dataset the case ran in, via `dataset_id` and `artifact_ids`. Datasets are only ever soft-deleted, so they stay readable; if a dataset (or an artifact) is purged from the eval database, its case shows no graph (or no artifact).

Only the trajectory *reference* is stored in the database; the trajectory is the file `<trajectory_id>.json` in the trajectory directory. The runner stores the files in an `atif/` directory next to the eval database (`build/atif/` by default) so the IDs stay resolvable; `-atif <dir>` changes it. `gb_case_runs_meta_knowledge_trajectories.path` records where each file went.

**Status and verdict.** The `status` of a run (experiment run, eval run or case run) is its *lifecycle*, never a verdict: `pending`, `running`, then `completed` (it ran to the end), `errored` (it could not run to the end; `error` says why) or `cancelled`. How it went is a separate field of a completed case run, its `verdict` (`pass` or `fail`) and its `score` (0 to 1). A run's `counts_*` are one count per status (`total`, `pending`, `running`, `completed`, `errored`, `cancelled`) and, of the completed case runs, `passed` and `failed`; every case is in exactly one of the five status counts, `pending` being the cases not reached (the ones left when a run is cancelled), and `total` is the number of cases the run is to execute. The schema's `CHECK`s enforce the sets.

| | eval run | case run |
|---|---|---|
| knowledge | `running`, then `completed`, `errored` (the executor could not go on) or `cancelled` (Ctrl-C) | `completed` with the verdict `pass` (every check held) or `fail` (a check did not hold, or the answer lacks an expected string; `problems` lists them), or `errored` (it could not be run to the end) |
| training | the same | `completed` with the verdict `pass` (the judge's score is at least 4 of 5) or `fail`, or `errored` (the model or the judge errored) |

A case that errors does not stop the run: it is an `errored` case run and the run goes on. The exit status of the knowledge runner is 1 if any case did not pass.

## Runner

```
./run_evals.sh [-experiment name] [-experiment-desc text] [-v] [case-name ...]
```

`-experiment` names the experiment; it is created on first use and later runs with the same name are further runs of it (`-experiment ""` runs the evals on their own, with no experiment run). Without `-experiment`, a run that picks one eval with `-eval` is named after that eval (it is targeted), and any other run (all the evals) is named with its start time (`YYYY-MM-DD_HH-MM-SS`), so it is unique. The runner records into the eval database (`-db`, default `build/gligabao-eval.db`), which it never resets; the datasets of a case run are named `<case>_run<eval run id>`. It prints the status and cost of the run at the end.

## From Go

```go
r := runner.New(d, store)             // d: the eval database's *sql.DB; store: from evals.StoreFor(backend)
def, err := r.SyncEval(ctx, spec)     // put an eval of the files in the database as defs
xd, err := r.EnsureExperiment(ctx, "baseline", "...", []core.EvalDefID{def.ID})   // get-or-create the experiment def
xr, err := r.StartExperimentRun(ctx, xd, core.Params{"models": models})           // start a run of it
run, err := r.RunEval(ctx, def, executor, runner.EvalOptions{ /* ExperimentRunID, Params, ... */ })
err = xr.Add(ctx, run)                // the experiment run sums the counts and the cost of its eval runs
err = xr.Finish(ctx, nil)
```

`RunEval` records the eval run (`running`) and gives an `EvalRecorder` to the executor of the type (`knowledge.Executor`, `training.Executor`), which calls `StartCase` and `FinishCase` (or `RecordCases`) for each case and so rewrites the eval run as the cases finish. Reading is `db.Store` (`GetEvalRun`, `ListCaseRuns`, `ListExperimentRuns`, `ListCaseHistory`, `FindKnowledgeTrajectory`, ...): a case run comes with its metadata and, for a knowledge one, its trajectory references; `FindKnowledgeTrajectory` leads from a trajectory ID back to its case run, eval run and experiment.

## Admin UI

With the admin UI enabled (`serve --admin-ui`, see the README), the **Evals** block shows the experiments of the eval database (`--eval-db`; without it the block has nothing to show): totals (experiments, runs, distinct cases, the case runs by their counts, cost), the experiment list (with the runs of each by status) and, by clicking an experiment, its runs. The UI shows the model's own words, not statuses of its own: a run and a case run have the status of `internal/evals/core` (`pending`, `running`, `completed`, `errored`, `cancelled`), a case run also its verdict (`pass` or `fail`, none if it has none) and score (and, for a [rerun](#rerunning-a-case-with-other-models), `rerun`: `{of, remember_model, query_model, remember_reasoning, query_reasoning}`), and a run its counts (`total`, `pending`, `running`, `completed`, `errored`, `cancelled`, `passed`, `failed`), which the JSON carries as `status`, `verdict`, `score` and `counts`. The history of a case plots its verdict (or its status when it has no verdict). Clicking a run opens its cases; expanding a case shows its answer, all its checks (passed and failed) and error, plus its ATIF traces. Each case also has a **View graph** button that opens the knowledge graph it built, read live from the case's dataset, in the same graph view as the datasets' **View graph** (`showGraphAt` in `graph.ts`). Next to it, **View temporal changes** opens the same plot as the **Temporal changes** of a [remember run](../remember/remember.md#admin-ui): what the remember calls of the case did to the facts over event time (created, confirmed, ended, invalidated, superseded), with the reference times of the texts and the table of events, for all the calls of the case together; it is read from the case's dataset too. Opened for a case, the plot also has a **Checks layer** (toggled with the button at its side): for each fact the case expects (`expect_edges`), a lane under the fact's row draws the expected span (`valid_at` to `invalid_at`, or open) on the same time axis as the stored fact, with a teal diamond (tick) for each check that held and a magenta one (cross) for each that failed (`stored`, `valid_at`, `invalid_at`, `ended`, `superseded`), and a bold magenta stretch (with `Δ`) for the gap between the expected and the stored time. An expected fact that was never stored gets a row of its own (*not stored*). The checks are read from the check texts of the case run and the expectations from the case's definition now (`GET case_runs/{id}/debug`), so a definition edited after the run can leave a check without a diamond (drawn hollow). The layer is drawn under the facts and never covers their dots and lines; the **Expand** button under the plot makes it wider and taller. Each case also has a button that opens the **case modal** (labelled **Debug & commentary** for a case that failed or errored, **Case details** for the others): everything about the case in one place, so a failure can be debugged against the LLM's advice. On the left are the checks (assertions and conditions) that failed and the ones that held, one list under the other, the error if the case did not run to the end, the answer given, and collapsible parts with what the case was given as it ran (the question and the texts remembered) and what its definition expects and its settings now, and its ATIF traces. On the right is the **LLM commentary and recommendation**: for a case that failed or errored, **Ask LLM for commentary** (with the model to use, `claude-sonnet-5-5` by default) sends the case to the LLM with the same prompt as the runner's [`-commentary`](knowledge.md#eval-commentary-debugging-a-failed-case) (the checks, the answer, the case definition and the ATIF trajectories of its calls), waits for the answer, stores it with the case run (`gb_case_run_commentaries`) and shows it (Cause, Where, Evidence, Suggestion and one Final advice, with its model, tokens and cost); **Ask again** adds another, and earlier ones stay listed under it. The commentary is never sent without the click, and its cost is not part of the case's or the run's. Above the commentary, a case that has ended has **Re-run this case with another model** (see [Rerunning a case with other models](#rerunning-a-case-with-other-models)). A case that was re-run also has a **Re-runs** table above the commentary, one row per re-run (including re-runs of re-runs): the model used for the **remember** pipeline and for the **query** with their thinking levels (*as it ran* when that pipeline kept them) and the final pass or fail (the status instead while it has none: running, errored, cancelled); **Open** opens the re-run as a case of its own. A case whose calls got a warning (a model that refused the thinking level, see [Reasoning](../remember/remember.md#reasoning)) has a **Warnings** section. The case modal is independent of the Evals view (`admin_ui/src/case_modal.ts`; the shared types and helpers are in `eval_common.ts`), so any view (the Evals view, the Bookmarks view) can open it and closing it leaves you where you were. **☆ Bookmark** on a case (here and in the run's case details) [bookmarks](../pipeline.md#bookmarks) it. The head of the modal has the **Knowledge graph** and **Temporal plot** buttons (the same views as below, for the case's dataset), so the graph the LLM worked from is one click away. Each trace also has a **View artifacts** button: the stored artifact for a `remember` call, the source artifacts of the answer for a `query`; they are read from the case's dataset. **View trace** draws a trajectory as a labeled process flow (d3): start → steps (system / user / agent; edges are labeled with the time between steps) → tool calls (`calls`) → tool results (`returns`) → end. Clicking a node shows its full content (message, reasoning, arguments, result, tokens, cost).

The JSON behind it is under `/v1/gb/admin/api/evals`: `GET /` (overview), `GET /experiments/{id}`, `GET /runs/{id}`, `GET /runs/{id}/web-searches` (the [web searches](../web-search.md#admin-ui) each case made, read from its trajectories), `GET /case_runs/{id}/graph` (the graph of the case's dataset), `GET /case_runs/{id}/temporal` (the temporal changes of the case's dataset: `case_run_id`, `artifact_ids`, the artifacts the case's remember calls stored, `artifacts` and `events`, as in `GET /remember-run-temporal`, oldest first; `404` for a case without a dataset), `GET /experiments/{id}/history?eval=..&name=..` (the results of one case over the experiment's runs) and `GET /case_runs/{id}/debug` (what the case modal shows: `eval`, `name`, `status`, `verdict`, `error`, `answer`, `problems` and `passed_checks`, the `input` as it ran, the `expected` checks and `params` of the case def as they are now, `dataset_id`, `commentable` (the case failed or errored), `commentary_enabled` (the server has an LLM), `default_model`, the `commentaries` made so far, newest first, `cost_usd`, `started_at` and `finished_at` (absent while it runs), `warnings` (what the case's calls got through but the operator should know, read from its trajectories, e.g. a model that does not take the thinking level asked for; absent when there are none), `rerun` (`{of, remember_model, query_model, remember_reasoning, query_reasoning}`, only when the case run is itself a rerun), `reruns` (the re-runs of this case run, and of those re-runs, oldest first, each `{case_run_id, of, remember_model, query_model, remember_reasoning, query_reasoning, status, verdict, cost_usd}`; empty when there are none, or when the case run is not in an experiment run) and `rerun_options` (`{models, reasoning}`, the models a rerun can pick, sorted, and the thinking levels; absent when the server cannot rerun); it also serves a case run that is still running; `404` for an unknown or non-knowledge case run), `POST /case_runs/{id}/commentary` (asks the LLM for a commentary, stores it and returns it as `{id, case_run_id, model, text, input_tokens, output_tokens, cost_usd, created_at}`; the optional body `{"model": "..."}` picks the model; `400` for a case run that did not fail or error, `404` for an unknown one, `503` when the server has no LLM, `502` when the LLM call failed; it blocks until the LLM answers), `POST /case_runs/{id}/rerun` (reruns the case with other models, see [below](#rerunning-a-case-with-other-models); body `{"remember_model": "..", "query_model": "..", "remember_reasoning": "..", "query_reasoning": ".."}`, each optional; `202` with `{case_run_id, eval_run_id, experiment_run_id}` of the new case run once it is recorded, and the rerun goes on in the background; `400` for a model that is not in the price table or an unknown thinking level, `404` for an unknown case run, `409` for a case run that cannot be rerun or when another rerun is in progress, `503` when the server has no LLM) and `GET /trajectories/{trajectory_id}`. A trajectory is served only if an experiment recorded its ID. Its file is read from the `atif/` directory next to the eval database, then from the `path` stored with the reference, so the server must be able to read the directory the evals wrote to.

## Rerunning a case with other models

The case modal of a case that has ended has a **Re-run this case with another model** section, to find out whether a more powerful model gets the case right. For each of the two pipelines, **remember** and **query**, two dropdowns (one under the other, one column per pipeline) pick the model and the **thinking** (reasoning) level. The models are the LLM models of the price table (the built-in prices plus the `[prices]` of the config); the levels are `none`, `low`, `medium` and `high`. The first option of each, *as it ran*, leaves that pipeline's models, or its levels, as they were; `none` is a choice of its own (no thinking). **Re-run case** starts the rerun.

**Models are not set per stage.** Underneath, models are per stage (`extract_graph`, `summarize_chunk`, `resolve_edges`, `web_search`, `resolve_series`, `detect_geo` for remember; `query` and `detect_geo` for the query; the `models` of a case or of the runner's `-models`), but there is no per-pipeline default in the eval path, so the rerun makes one: the model picked for a pipeline is used for **every** LLM stage of it (`knowledge.PipelineModels`; `extract_image` is left out, the cases never run it). It wins over the case's own `models`. The same goes for the thinking level (`knowledge.PipelineReasoning`): one level per pipeline for every LLM stage of it, winning over the `reasoning` of the case and of the run. Everything else stays as the case run had it: the runner's `models` and `reasoning` of the original eval run (a stage the rerun does not set keeps its model and level), the checks and settings of the case as the case def has them now, and the geo setting.

**What is rerun.** The same case, with the input the case run was given (the texts of its files as they were read then, not as the files say now), in a dataset of its own (`<case>_run<new eval run id>`). The rerun is recorded like any run: as a new **eval run** with that one case, in the **experiment run that owns the case run**, so it is in the experiment's list of runs (the run modal shows it as another row of the case, tagged *rerun*), the experiment run's counts and cost include it, and the case's history has another point. The new eval run's `params` say what it is: `rerun_of` (the case run that was repeated), `remember_model`, `query_model`, `remember_reasoning` and `query_reasoning` (the models and levels picked; missing: kept), `cases`, and the `models`, `reasoning` and `geo` it ran with. A case run that has no experiment run (the eval was run on its own) is rerun on its own. A rerun of a rerun repeats the same case again, with the models picked now over the original run's.

**Following it.** The rerun goes on in the server, in the background (it takes as long as the case does, and stops, recorded as cancelled, when the server shuts down). The endpoint answers as soon as the new case run is recorded as `running`, and a **rerun modal** opens on top of the case modal: while it runs it shows its status and time (it reads `GET /case_runs/{id}/debug` every few seconds), and when it ends its result next to the case run it repeated (models and thinking levels, status, verdict, cost, duration), its checks and answer, its traces and, with the buttons of the head, the graph and temporal plot it built. Closing the modal does not stop the rerun; it can be opened from the run's list like any case, with its commentary.

**Limits.** One rerun runs at a time (`409` otherwise). A case run cannot be rerun while it has not ended, while its experiment run is still running (the runner would overwrite the counts of the run when it ends; an experiment run left `running` by a killed runner stays that way), or when its case def or eval is gone (`409`). The server needs its LLM (the Anthropic key) and opens the eval database (`--eval-db`) with its own connection to write the rerun, with the same embedding store as the runner (chromem next to the file); it does not need the runner. The rerun's ATIF trajectories are written to the server's trajectory directory (`memory_core.TrajectoryDir`), and the trajectory references keep the path, so the admin UI finds them wherever they went. The code is `knowledge.Rerunner` (`internal/evals/knowledge/rerun.go`), handed to the server through `server.Options.EvalRerunner`, because the package imports the server and the server cannot import it.
